Section 1.1

Executive Summary

Motqin is an AI-driven study companion built to help students focus, learn, and track academic progress through five interconnected modules: an AI Teacher, an App Blocker / Focus System, a Quiz & Spaced-Repetition tracker, Competitions & Gamification, and a Smart Planner that ties everything together. This report covers the frontend application only — a Next.js 16 / React 19 codebase that consumes a separate .NET backend API.

As of this report, the frontend has a working, production-shaped authentication system (phone OTP, Google OAuth, Facebook OAuth, JWT access/refresh tokens with cross-tab coordination), a functioning subjects → lessons → questions browsing flow wired to live backend endpoints, a first working version of the AI Teacher chat (text + generated speech), and fully designed but not-yet-backend-connected screens for the Smart Planner and Subscription/Checkout flow. The App Blocker and Competitions/Gamification modules described in the product vision do not yet exist as working frontend features — they currently appear only as marketing copy on the landing page and as line items in the subscription plan descriptions.

What's solid Authentication (with a genuinely sophisticated multi-tab token-refresh system), API/service layer, subjects & lessons data fetching, and the AI Teacher chat's happy path are implemented against real endpoints and follow a consistent, scalable architecture.
What's designed but not wired up The Smart Planner UI (weekly view, day cards, mood, focus sessions) runs entirely on local mock data (app/data/days.ts) with no backend calls. The Subscription/Checkout flow computes real pricing but the "Confirm payment" button only shows a toast — no payment gateway is integrated yet.
What's missing entirely App Blocker (focus/distraction blocking, Supervisor Mode), spaced-repetition scheduling logic, Competitions/leaderboards, and gamification (achievements, points) have no frontend implementation yet — they exist only as product vision and UI copy.

The remainder of this report walks through the technology choices, the architecture that ties the app together, a page-by-page look at what's built, an honest gap analysis against the five core pillars, and a prioritized set of recommended next steps.

Section 1.2

Project Vision & Core Pillars

Motqin's product vision centers on five interconnected modules, all coordinated by a central Smart Planner. The frontend's job is to expose each module through a consistent, adaptive interface. The diagram below shows how the pillars are meant to relate to one another — the Smart Planner is the hub that reads from and writes to every other module.

The five pillars, as specified

AI Teacher

Personalized tutor trained on predefined subjects. Adjusts explanation depth to student level; supports Q&A and step-by-step walkthroughs.

App Blocker (Focus System)

Blocks distracting apps on a time- or task-based schedule, integrated with the planner. Includes a Supervisor Mode that only a parent/mentor can override.

Quiz & Progress Tracking

AI-generated quizzes at multiple difficulty levels and formats, with spaced-repetition scheduling for weak or old material.

Competitions & Gamification

Leaderboards, achievements, and peer comparison to sustain motivation and engagement over time.

Smart Planner (the hub)

Central, highly customizable scheduler. Times spaced-repetition reminders, detects the student's most productive hours, auto-schedules focus sessions, and drives the App Blocker's behavior — the one system every other module reports into.

Section 2.1

Core Framework & Language

The frontend is a single Next.js application using the App Router, written entirely in TypeScript, styled with Tailwind CSS v4. Below is how each core piece is actually used in this codebase — not just what it is in general.

next v16.1.4
Framework

App Router with route groups — (public), (auth), (protected) — each with its own layout.tsx. Client components are marked with "use client" throughout (the app is effectively CSR-first: almost every page fetches data client-side via React Query rather than using Server Components for data loading). next/font/google loads Inter, Geist, Geist Mono and Cairo (for Arabic) as CSS variables in the root layout. next/image and next/navigation (useRouter, useParams, useSearchParams) are used across auth guards and dynamic subject/lesson routes.

react / react-dom v19.2.3
UI Library

Function components with hooks throughout; no class components. React 19 is required by Next 16.

typescript ^5
Language

Domain types are hand-written per feature (planner.types.ts, auth.types.ts, motqin.types.ts) rather than generated from the backend's OpenAPI schema — worth automating later (see Roadmap).

tailwindcss v4 · @tailwindcss/postcss
Styling

Tailwind v4's CSS-first config (no tailwind.config.js; theme lives in globals.css via @theme/CSS custom properties). Dark mode and page-specific theme tokens (e.g. --surface, --sidebar-bg, --input-border) are consumed with var(--token) inside Tailwind's arbitrary-value syntax, e.g. bg-[var(--surface)].

sass
Styling

Used for a small number of legacy/utility stylesheets (e.g. notfound.css compiled from Sass) alongside Tailwind.

Rendering strategy note Nearly every route in this app is a Client Component ("use client") that fetches its own data with TanStack Query. This is a pragmatic choice for a fast-moving student project, but it forfeits some of Next.js's Server Component benefits (smaller client bundles, server-side data fetching, better first paint). Worth revisiting selectively — see Recommended Next Steps.

Section 2.3

Data, State, Forms & Auth Libraries

@tanstack/react-query v5.101.1 (+ devtools)
Server state

The single source of truth for anything that comes from the backend — subjects, lessons, questions, current user, and every auth mutation (login, register, verify, logout). One QueryClient is created per app instance in QueryProvider and provided at the root, above every other provider except theming.

axios v1.18.0
HTTP client

A single configured axiosInstance (app/lib/axios.ts) is the only way the app talks to the backend. A request interceptor attaches the bearer token; a response interceptor centrally handles 401 → silent token refresh → retry, and turns every other failure into a toast. See Section 3.4 for the full refresh-token design.

zustand v5.0.14
Client state

Lightweight global store used narrowly — currently just useAuthStore, which holds transient sign-up state (phone number, OTP resend cooldown/remaining count) that needs to survive navigation between the sign-up → verify-phone → complete-profile screens without being persisted or sent to the server.

react-hook-form v7.71.1 + @hookform/resolvers + zod v4.3.6
Forms & validation

Every form (sign-in, sign-up, add-question, complete-profile) uses useForm with a zodResolver against a schema defined in app/lib/validators/, giving typed, runtime-validated form state with minimal boilerplate.

jwt-decode v4.0.0 (+ hand-rolled decode)
Auth

Used alongside a small manual base64/JWT payload decoder in auth-storage.ts (getAccessTokenExpiry) to schedule the proactive token-refresh timer.

@react-oauth/google v0.13.5
Auth provider

Wraps the app in GoogleOAuthProvider (providers/googleProvider.tsx) using NEXT_PUBLIC_GOOGLE_CLIENT_ID; the GoogleSignIn component renders Google's button and forwards the ID token to useGoogleLogin.

Facebook SDK (via custom provider)
Auth provider

FacebookProvider.tsx loads the Facebook JS SDK (NEXT_PUBLIC_FACEBOOK_APP_ID) into <head>; facebook-auth.services.ts wraps FB.login in a Promise for the sign-in page to call.

Why this stack works for Motqin

React Query + a thin Axios layer keeps every screen's server data in sync without a hand-rolled cache. Zustand is intentionally used only where React Query would be the wrong tool (transient, non-server UI state) — a good discipline that keeps state management legible. Zod + react-hook-form gives the auth and question-authoring forms real validation with very little code per form.

Section 3.1

Route & Folder Architecture

The App Router is organized into three route groups by access level. Route groups (parenthesized folder names) don't affect the URL — they let each area define its own layout and guard logic.

Guarding happens redundantly: (protected)/layout.tsx (checks authStorage.getAccessToken(), redirects to /sign-in) and a standalone components/auth/ProtectedRoute.tsx wrapper both do the same client-side check. A third, unrelated middleware.ts at the project root implements a similar idea but is currently disabled and out of sync with the real route names — see Section 4.2 and 5.2.

Section 3.2

Provider Composition & Rendering Model

Every page renders inside a fixed stack of context providers, mounted once in app/layout.tsx via a single <Providers> component. Order matters: each provider only has access to what's above it.

Outside this stack, but still root-level: a FacebookSDK script tag injected in <head>, and a globally mounted <Toaster> (sonner) configured for RTL, positioned top-center, styled per toast type (success/error/warning/info) to match the design tokens.

Section 3.3

Data Flow: Component → API

Every real data operation in the app follows the same four-layer path. This consistency is one of the codebase's strongest architectural traits — a new feature can be added by following the same recipe every time.

Concrete example — Subjects page

  1. SubjectsPage calls useGetSubjects() — a thin React Query useQuery wrapper.
  2. The hook's queryFn calls a typed service function that knows the URL (API_ROUTES.SUBJECTS.GET_ALL) and return shape.
  3. The service calls the shared axiosInstance, which injects Authorization: Bearer <token> and unwraps the backend's response envelope.
  4. On error, the response interceptor shows a toast automatically — the component itself only needs to render isPending / isError states, never handle errors directly.
Why this matters for the graduation write-up This is a textbook layered architecture (presentation → data-access hook → service → HTTP client), which keeps components free of fetch/error-handling logic and makes the same pattern trivially reusable for new features (e.g. adding the Planner's real API integration is "just" writing planner.service.ts + a matching hook).

Section 3.4

Authentication & Token Refresh Architecture

This is the most architecturally mature part of the frontend. Access tokens are short-lived JWTs; refresh tokens are longer-lived and single-use (rotated on every refresh). Two problems had to be solved beyond a textbook interceptor: multiple open tabs refreshing at once, and distinguishing a truly expired session from a transient network failure.

Engineering highlight Handling refresh-token rotation across multiple tabs correctly is a genuinely non-trivial distributed-coordination problem — most student (and many production) apps skip it and end up with random logout bugs when a user has two tabs open. This is a strong section to expand on in the graduation write-up's "technical depth" discussion.

Route guarding

Every route under (protected) checks authStorage.getAccessToken() in a useEffect and redirects to /sign-in if absent — implemented identically in (protected)/layout.tsx and again in the standalone ProtectedRoute component. This is a client-side-only guard: because every protected page is a Client Component, there's a brief flash where null is rendered before the redirect fires, and the guard offers no protection against a user with dev tools directly hitting the backend — the backend's own JWT validation is the real security boundary here, as it should be.

Observed rough edges A few debug console.log calls remain in shipped code (e.g. useGoogleLogin, the home page, subject pages) — harmless but worth stripping before a public build. Route guarding is duplicated across three places that don't agree with each other: (protected)/layout.tsx and ProtectedRoute.tsx both correctly check localStorage for a token, but a third file, middleware.ts, also exists at the project root with its own (currently disabled) guard — isLoggedIn is hardcoded to true and its route names (/signin, /signup, /dashboard) don't match the app's real routes (/sign-in, /sign-up, /). It has no effect today, but its presence is worth knowing about (see Section 5.2).

Section 4.3

AI Teacher (Chat Interface)

Route: /Ai-Teacher. A three-part chat layout — subject sidebar, scrolling message window, and a text input with a (currently inert) mic button — built as its own mini client-state app (ChatLayoutt) independent of React Query, since chat messages aren't a cached server resource here.

Fig. 4.3 — Reconstructed from ChatLayout.client.tsx, ChatWindow.tsx, ChatInput.tsx, Sidebar.tsx.

How a message round-trip works today

  1. User sends text → sendMessage() POSTs to {'{NEXT_PUBLIC_AI_API_URL}'}/chat with {'{'} message, lesson_id: "default", request_type: "explain" {'}'}.
  2. The reply text comes back, then fetchSpeech() immediately POSTs that reply to a hardcoded http://127.0.0.1:8000/talk to get a TTS audio blob.
  3. The audio blob is converted to an object URL and attached to the assistant's message bubble as an inline <audio> player.
Known issues to fix lesson_id is always the literal string "default" — the chat isn't yet aware of which subject/lesson the student is on, even though the sidebar visually implies lesson context. The TTS URL is hardcoded to localhost instead of using NEXT_PUBLIC_AI_API_URL, so voice replies will silently fail outside local development. No conversation history is persisted — refreshing the page loses the chat.

Section 5.1

Gap Analysis Against Core Objectives

Measuring the current frontend against the five pillars from the original product brief:

1. AI Teacher — personalized, adaptive tutor

Partially met Chat UI and a working text+voice round-trip exist. Missing: awareness of which subject/lesson the student is in, adjustable explanation depth ("simplify / deepen"), and any persistence of the conversation.

2. App Blocker — time/task-based blocking with Supervisor Mode

Not met No frontend implementation. This is also the pillar hardest to build as a web app in the first place — see the recommendation on native/OS-level scope in Section 5.2.

3. Quiz & Progress Tracking with spaced repetition

Partially met Question browsing/authoring is real; quiz-taking, scoring, history, and spaced-repetition scheduling are all unbuilt.

4. Competitions & Gamification

Not met Exists only as a hardcoded marketing card ("Rank #3 · 2,450 Points") and a line item in subscription-plan copy.

5. Smart Planner — the central, adaptive hub

Partially met The UI and data model are well-designed and already anticipate the real product (AI-sourced tasks, focus sessions, mood tracking), but it currently has zero connection to a backend, and none of the "detects your most productive hours" / "auto-schedules focus sessions" intelligence exists yet.

Headline gap Per the project brief, "all modules MUST be interconnected." Today, every module is an island — Planner doesn't know about quiz results, quiz results don't feed spaced repetition, and nothing talks to a (non-existent) App Blocker. Closing this gap is more about backend + integration design than frontend polish, but the frontend's job is to be the layer that visibly ties it together once those pieces exist.

Section 5.2

Recommended Next Steps (1/2)

Prioritized by leverage: what unlocks the most product value per unit of engineering effort, given what's already built.

1

Wire the Planner to a real backend

The UI and data model already anticipate the real product. Add planner.service.ts + React Query hooks following the exact pattern used for subjects/lessons/questions; replace app/data/days.ts with fetched data. This is the single highest-leverage change since the Planner is the specified integration hub for every other module.

2

Give the AI Teacher lesson context

Pass the real subjectId/lessonId into sendMessage() instead of the hardcoded "default"; fix the hardcoded localhost:8000 TTS URL to use NEXT_PUBLIC_AI_API_URL; persist chat history (even just per-lesson in React Query cache) so it survives navigation.

3

Build the quiz-taking experience

The /quiz route the "ابدأ" button links to doesn't exist yet. This is the natural next screen given how solid the questions data layer already is: question runner, scoring, and a results summary that can later feed spaced-repetition scheduling.

4

Add a real payment gateway to Checkout

The pricing/discount math and UI are done — only the "Confirm payment" action needs a real provider (e.g. Paymob or Fawry, both common for EGP transactions) behind it.

5

Fix and consolidate route guarding into middleware.ts

A middleware.ts already exists at the project root but is inert (isLoggedIn hardcoded to true, and it references route paths — /signin, /dashboard — that don't match the app's actual routes). Since auth tokens live in localStorage, real middleware can't read them directly (middleware runs on the edge, before client JS); the fix is to also mirror the access token into an httpOnly cookie on login so middleware can check it server-side, then delete the two duplicated client-side checks in (protected)/layout.tsx and ProtectedRoute.tsx in favor of that one middleware. This removes the current logged-out UI flash and the triplicated logic.

Section 5.2

Recommended Next Steps (2/2)

6

Design the App Blocker's realistic scope

True cross-app blocking isn't achievable from a web app's sandbox — it needs a companion mobile app (Android Accessibility/Usage-Stats APIs, or iOS Screen Time API) or a browser/desktop extension. Recommend scoping an MVP now: a "Focus Session" timer inside Motqin itself (blocks navigation within the app, shows a distraction-free mode) as a stepping stone toward real device-level blocking, and documenting the native-app requirement clearly for the project's next phase.

7

Introduce a minimal Competitions/Gamification model

Start small: points for completed quizzes/planner tasks (data already tracked in PlannerDay/Task), a simple leaderboard endpoint, and an achievements list — enough to replace the current hardcoded homepage stats with real ones.

8

Generate API types from the backend's OpenAPI schema

Domain types are currently hand-maintained per feature.
