Mentors & Sign-in API

A student can invite people as mentors and let them see their performance and their distraction blocker. One mentor can also lock the blocker, so changing it needs a code from that mentor. This guide also covers the sign-in changes: Google now asks for a phone confirmed by WhatsApp, and Facebook is gone.

How it works

stateDiagram-v2
  direction LR
  [*] --> Pending: student sends a request
  Pending --> Active: mentor accepts
  Pending --> Declined: mentor declines
  Pending --> Cancelled: student cancels
  Active --> Ended: mentor unlinks (any time)
  Active --> Ended: student ends (no privileges left)
  Active --> Ended: mentor approves the student's unlink request

sequenceDiagram
  participant S as Student app
  participant API as Motqin API
  participant M as Mentor page
  S->>API: update or delete a schedule
  API-->>S: 400 blocker_locked
  S->>API: POST blocker-unlock/request
  API-->>S: codeExpiresAt (10 minutes)
  M->>API: GET mentees/id
  API-->>M: unlockCode 482913
  M-->>S: tells the code (in person or by message)
  S->>API: POST blocker-unlock/verify
  API-->>S: unlockedUntil (15 minutes)
  S->>API: update or delete the schedule again
  API-->>S: 200

flowchart LR
  G[POST google] -->|account with a confirmed phone| T([token])
  G -->|needsPhone: true| R[POST google/phone-request]
  R -->|code on WhatsApp| V[POST google/phone-verify]
  V -->|phone already has an account| L[Google linked to that account]
  V -->|new person| N[new account, or the guest trial upgraded]
  L --> T
  N --> T

PUT/api/mentorship/{id}/privilegesnewstudent

Choose what this mentor can see or do. Send all three switches as you want them. Switching one on applies at once. Switching one off waits for the mentor's approval, and shows in removalRequested until then.

  • canLockBlocker: only one mentor can hold this privilege. With it, changes need this mentor's code. It also turns on canViewBlocker.

Part 4

Sign-in changes

Google sign-up now confirms a phone by WhatsApp. Sign-in codes go out by WhatsApp, wrong codes are limited, and the Facebook button goes away.

Codes in responses. While WhatsApp codes are switched off on the server (today's setting), the code still comes back in message, e.g. "OTP sent successfully. Debug Code: 690210". Once the server switches them on, the code arrives on WhatsApp and message is just "OTP sent successfully.". Development servers always show it.

Google
POST/api/auth/googlechangedanyone

Sign in with Google. Every Google account now needs a confirmed phone. If the account exists and has one, you get the token as before. If not, you get needsPhone: true; nothing is created, and the app continues with the two phone steps below, sending the same Google ID token. Existing Google users already count as confirmed.

Part 5

Manual test in Swagger

About 20 minutes. Open Swagger in two browser tabs: one signed in as the mentor, one as the student. Steps 1 to 3 create the accounts; after that, each step says which tab to use. Keep WhatsApp codes switched off on the server so the codes show in the responses.

  1. mentor tabPOST/api/auth/test-phone-login

    No body. Copy token from the response, click Authorize, and paste it. This account (01094341573) is the mentor.

  2. student tabPOST/api/auth/phone-login-request
    { "phoneNumber": "01000000150" }

    Expect 200 with "message": "OTP sent successfully. Debug Code: 123456". Note the 6 digits.

  3. student tabPOST/api/auth/phone-verify, then POST/api/auth/phone-complete-signup
    { "phoneNumber": "01000000150", "code": "123456" }
    { "phoneNumber": "01000000150", "name": "طالب تجربة", "region": 1 }

    The first gives needsSignup: true; the second gives token.token. Authorize this tab with it. On a second run the number already exists: phone-verify then returns the token directly (token.token), so skip phone-complete-signup.

  4. student tabPOST/api/mentorship/requests
    { "phoneNumber": "01094341573" }

    Expect 200, "status": "Pending". Note the id; every step below uses it as {id}. Send it again: 400 mentor_request_exists.

  5. mentor tabGET/api/mentorship/requests/incoming, then POST/api/mentorship/{id}/accept

    The request shows with the student's name and phone. Accept: 200, "status": "Active". Accept again: 400 mentorship_not_pending.

  6. mentor tabGET/api/mentorship/mentees/{id}

    today, week and blocker are all null, because nothing is shared yet.

  8. mentor tabGET/api/mentorship/mentees, then GET/api/mentorship/mentees/{id}
